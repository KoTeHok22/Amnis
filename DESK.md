# DESK.md

## Тестовый отчет по Amnis

Дата теста: 2026-04-06

Среда:

- ОС: Windows
- Запуск: Docker Compose
- Браузер: Playwright MCP, Chrome, headless
- Основной viewport, доступный в сессии: 1280x720

## Что было проверено

### Запуск проекта

- Частичный запуск `db + redis + backend + frontend`
- Полный запуск всего `docker compose up -d`

### Backend

- `GET /health`
- `POST /register`
- `POST /login`
- Проверка фактического состояния схемы PostgreSQL

### Frontend через Playwright

- Загрузка лендинга
- Hero CTA `Начать толкование сна`
- CTA из карточек тарифов `Выбрать`
- Открытие модалки входа
- Переключение в регистрацию
- Отправка формы логина
- Отправка формы регистрации
- Открытие и полный проход `ResetPasswordModal`

## Краткая UX-оценка

### Что выглядит удачно

- На desktop-viewport лендинг визуально цельный: читаемая иерархия, сильная hero-секция, понятные CTA, хорошо отделены блоки `Как это работает`, `Возможности`, `Тарифы`.
- CTA-поток понятный: и главная кнопка, и кнопка `Выбрать` с тарифов открывают auth-модалку.
- `ResetPasswordModal` визуально и логически собран последовательно: телефон -> код -> новый пароль -> success.

### Что мешает реальной usability-оценке

- Полный пользовательский путь в чат не удалось провалидировать, потому что auth и backend сломаны на инфраструктурном уровне.
- Полноценную live-проверку mobile/narrow viewport через текущую Playwright-MCP сессию выполнить не удалось: viewport не менялся программно в доступном режиме. Поэтому адаптивность оценена только частично по desktop-рендеру и по наличию responsive-классов в UI.

## Найденные проблемы

### 1. Blocker: весь проект не поднимается командой `docker compose up -d`

Серьезность: Blocker

Шаги:

1. Выполнить `docker compose up -d` в корне проекта.

Ожидание:

- Поднимаются все сервисы, описанные в `docker-compose.yml`.

Факт:

- Запуск падает с ошибкой:
  `unable to prepare context: path "H:\Diplom\Влад\Amnis\TELEGRAM" not found`

Вывод:

- Объявленный в compose сервис `telebot` делает полный запуск проекта невозможным в текущем состоянии репозитория.

---

### 2. Blocker: backend объявляется healthy, но ключевая схема БД фактически отсутствует

Серьезность: Blocker

Шаги:

1. Поднять `db`, `redis`, `backend`, `frontend`.
2. Проверить `GET http://127.0.0.1:8000/health`.
3. Выполнить `POST /register` или `POST /login`.
4. Проверить таблицы в PostgreSQL через `docker exec amnis_db psql -U Amnis -d dream_interpreter -c "\dt"`.

Ожидание:

- После миграций таблицы `users`, `chats` и связанные сущности существуют.
- Auth endpoints работают.

Факт:

- `/health` возвращает `200 OK` и `{"status":"healthy"...}`.
- При этом `/register` и `/login` отвечают `500`.
- В логах backend:
  `psycopg2.errors.UndefinedTable: relation "users" does not exist`
- В PostgreSQL команда `\dt` возвращает:
  `Did not find any relations.`

Вывод:

- Healthcheck не отражает реальную готовность приложения.
- Миграции/инициализация БД считаются успешными, но рабочая схема отсутствует.
- Из-за этого весь auth и любые пользовательские сценарии, завязанные на БД, заблокированы.

---

### 3. Blocker: локальный frontend ходит не в локальный backend, а во внешний `https://api.jdh-team.ru`

Серьезность: Blocker

Шаги:

1. Открыть `http://127.0.0.1:3000`.
2. Открыть auth-модалку.
3. Заполнить логин или регистрацию.
4. Отправить форму.
5. Зафиксировать XHR через Playwright runtime.

Ожидание:

- При локальном запуске frontend обращается к локальному backend `http://127.0.0.1:8000` или к относительным локальным роутам.

Факт:

- Зафиксированы реальные запросы:
  - `POST https://api.jdh-team.ru/login`
  - `POST https://api.jdh-team.ru/register`
- В локальных логах backend после submit из браузера auth-запросов нет.

Вывод:

- Локально поднятый frontend не подключен к локальному backend.
- Из-за этого тестирование локального стенда через UI невозможно даже при работающем контейнере backend.

---

### 4. Blocker: auth через frontend ломается на SSL-ошибке внешнего API

Серьезность: Blocker

Шаги:

1. Открыть auth-модалку.
2. Ввести телефон и пароль.
3. Нажать `ВОЙТИ`.
4. Проверить browser console.

Ожидание:

- Пользователь авторизуется или получает корректную серверную ошибку приложения.

Факт:

- В console зафиксировано:
  `Failed to load resource: net::ERR_CERT_COMMON_NAME_INVALID @ https://api.jdh-team.ru/login`
- Параллельно frontend логирует:
  `Authentication error: {detail: Ошибка при входе}`

Вывод:

- Текущий auth-flow через UI неработоспособен.
- Пользователь не может перейти к чату и проверить основной продуктовый сценарий.

---

### 5. Major: пользователь получает слишком общую ошибку авторизации

Серьезность: Major

Шаги:

1. Повторить сценарий логина при текущей конфигурации.

Ожидание:

- Ошибка объясняет проблему или хотя бы подсказывает следующее действие.

Факт:

- В UI отображается только `Ошибка при входе`.
- Реальная причина при этом инфраструктурная: внешний URL + SSL mismatch.

Вывод:

- Ошибка не помогает пользователю понять, что произошло.
- Для отладки и для UX это слишком непрозрачная обратная связь.

---

### 6. Minor: отсутствует `favicon.ico`

Серьезность: Minor

Шаги:

1. Открыть главную страницу в браузере.
2. Проверить console/network.

Факт:

- Браузер получает `404` на `http://127.0.0.1:3000/favicon.ico`.

Вывод:

- Небольшой, но явный признак незавершенной frontend-сборки.

---

### 7. Minor / A11y: у password input отсутствуют `autocomplete`-атрибуты

Серьезность: Minor

Шаги:

1. Открыть auth-модалку.
2. Проверить console.

Факт:

- Playwright/Chromium сообщает:
  `Input elements should have autocomplete attributes (suggested: "current-password")`

Вывод:

- Это ухудшает доступность и удобство работы с менеджерами паролей.

## Что удалось подтвердить как рабочее

### Frontend / UX

- Лендинг загружается стабильно.
- Hero CTA открывает auth-модалку.
- CTA `Выбрать` в тарифах тоже открывает auth-модалку.
- Переключение login -> register работает.
- `ResetPasswordModal` открывается и его внутренний flow проходит до success-состояния без падения UI.

### Backend / Infra

- Контейнеры `db`, `redis`, `backend`, `frontend` поднимаются частично командой:
  `docker compose up -d db redis backend frontend`
- `/health` отвечает, хотя эта проверка сейчас ложноположительная с точки зрения бизнес-готовности.

## Общий вывод

На уровне визуального desktop-first UX продукт выглядит осмысленно и интуитивно: CTA понятны, структура лендинга хорошая, модальные сценарии оформлены последовательно.

Но в текущем состоянии приложение нельзя считать работоспособным end-to-end из-за трех критических блокеров:

1. Полный compose-стек не запускается из-за отсутствующего `TELEGRAM/`.
2. Локальный backend не имеет рабочей схемы БД, несмотря на успешные health/migration-сообщения.
3. Локальный frontend шлет auth-запросы во внешний `https://api.jdh-team.ru`, где они падают на SSL-проблеме.

Именно эти проблемы сейчас блокируют полноценную проверку chat-flow, профиля, оплаты и адаптивности authenticated-зоны.
