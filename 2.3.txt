2.3 Реализация серверной логики и хранения диалогов
Серверная часть приложения построена как прикладной API-слой, который связывает пользовательский интерфейс, реляционную базу данных, файловое хранилище контекста диалогов, очередь фоновых задач и внешний сервис генерации текста. Внутри этого слоя сосредоточены функции аутентификации, работы с профилем, управления чатами, обработки подписки и передачи сообщений интеллектуальному модулю. Такое разделение позволяет вынести вычислительную и интеграционную нагрузку из клиентской части и поддерживать единые правила доступа к данным и операциям (см.рис. 23).
```mermaid
flowchart LR
    UI[Клиентское приложение] --> API[Серверный API]
    API --> DB[(PostgreSQL)]
    API --> JSON[(JSON-хранилище диалогов)]
    API --> REDIS[(Redis)]
    REDIS --> WORKER[Фоновый воркер]
    API --> AI[Внешний AI-сервис]
    WORKER --> AI
```
Рис. 23. Серверный контур приложения и внешние зависимости
Организация запуска серверной подсистемы предусматривает проверку готовности базы данных, повторные попытки подключения и отдельный этап применения миграций. После этого дополнительно выполняется контрольная инициализация схемы средствами ORM. Такая последовательность выбрана для уменьшения числа ошибок на старте контейнеров, когда база данных и прикладной сервер поднимаются одновременно и могут быть готовы в разное время. В результате сервер получает более устойчивую процедуру ввода в рабочее состояние без ручного вмешательства.
Серверный API реализован по схеме типизированных HTTP-операций. Для входящих запросов используются формализованные модели данных, что позволяет проверять состав и типы полей до выполнения основной бизнес-логики. Практический эффект такого подхода состоит в том, что ошибки формата обнаруживаются на раннем этапе, а каждый маршрут API работает с заранее определенной структурой запроса. Для прикладной системы с регистрацией, чатами, подпиской и альтернативными способами входа это уменьшает число неоднозначных ситуаций при обмене данными между клиентом и сервером.
Подсистема аутентификации построена вокруг нормализованного номера телефона и токена доступа формата JWT. Номер телефона приводится к единому представлению за счет удаления посторонних символов и обработки префиксов, после чего используется как устойчивый идентификатор пользователя на уровне прикладной логики. После успешного входа сервер выдает токен ограниченного срока действия, который далее передается клиентом в заголовке авторизации. Такое решение избавляет сервер от хранения классической пользовательской сессии в оперативной памяти и сохраняет совместимость с отдельными клиентскими каналами доступа.
На защищенных маршрутах применяется единая схема проверки полномочий. Сервер декодирует токен, извлекает из него идентификатор пользователя, затем сверяет его с данными постоянного хранилища и дополнительно проверяет признак активности учетной записи. Только после этого выполняется целевая операция: получение профиля, обновление данных, отправка сообщения, создание чата или изменение подписки. Подобная последовательность делает авторизационную проверку повторяемой для разных частей API и не допускает выполнения защищенных действий при невалидном или устаревшем токене (см.рис. 24).
```mermaid
sequenceDiagram
    participant C as Клиент
    participant A as Серверный API
    participant J as JWT-проверка
    participant D as База данных
    C->>A: Защищенный запрос с токеном
    A->>J: Декодирование токена
    J-->>A: Идентификатор пользователя или ошибка
    A->>D: Поиск пользователя и проверка активности
    D-->>A: Данные пользователя или отсутствие записи
    alt токен валиден и пользователь активен
        A-->>C: Выполнение целевой операции
    else ошибка авторизации
        A-->>C: Ответ 401
    end
```
Рис. 24. Последовательность авторизации защищенного запроса
Регистрация нового пользователя предполагает несколько этапов серверной обработки. После нормализации номера телефона и проверки его формата система убеждается в отсутствии существующей записи с тем же идентификатором, затем вычисляет криптографический хэш пароля и сохраняет новую учетную запись. Дата рождения принимается в стандартизированном текстовом формате и преобразуется во внутреннее представление серверной среды. На выходе пользователь получает токен доступа и минимальный набор собственных данных, необходимых для немедленного начала работы с приложением.
Подсистема управления профилем охватывает чтение и изменение персональных данных, а также смену пароля. При запросе профиля сервер возвращает идентификатор, номер телефона, имя, дату рождения, количество доступных анализов и дату создания записи. При обновлении профиля выполняется повторная проверка токена и преобразование даты рождения, после чего измененные сведения фиксируются в базе данных. Смена пароля выполняется только после подтверждения текущего секрета и проверки минимальных требований к новому значению. Такая модель разграничивает операции чтения и изменения, но использует единый механизм идентификации пользователя.
Отдельную ветвь серверной логики образует управление подпиской и количеством доступных анализов. После подтверждения оплаты сервер увеличивает счетчик доступных анализов и вычисляет новую дату окончания доступа как смещение от текущего времени на заданное число суток. При последующем запросе сведений о подписке возвращаются остаток анализов, дата истечения и рассчитанное количество оставшихся дней. Для прикладной логики это означает, что платежное состояние не является абстрактным флагом, а хранится в явных числовых и временных полях, пригодных для дальнейших проверок и отображения в интерфейсе (см.рис. 31).
```mermaid
sequenceDiagram
    participant C as Клиент
    participant A as Серверный API
    participant J as JWT-проверка
    participant D as База данных
    C->>A: POST /payment/success
    A->>J: Проверка токена
    J-->>A: Идентификатор пользователя
    A->>D: Загрузка текущего профиля
    A->>D: Увеличение available_analyses
    A->>D: Обновление subscription_expiry
    D-->>A: Подтверждение транзакции
    A-->>C: Новое количество анализов
```
Рис. 31. Обработка подтвержденной оплаты и обновление профиля
Модель хранения данных построена на сочетании реляционной схемы и файлового контекста диалогов. В реляционной базе данных сохраняются устойчивые сущности, для которых критичны связи, ограничения уникальности и выборки по пользователю. Полная история сообщений каждого чата, напротив, сохраняется в отдельных JSON-документах. Такое решение уменьшает нагрузку на реляционную схему при работе с длинными переписками и позволяет отделить метаданные чатов от содержимого их сообщений. В результате система получает гибридную модель хранения, адаптированную к различной природе данных (см.рис. 25).

Рис. 25. Основные сущности постоянного хранения
Центральной сущностью предметной области является пользователь. Для него хранятся номер телефона, имя, дата рождения, хэш пароля, признак активности, счетчик доступных анализов, дата окончания подписки и временные метки создания и изменения. Номер телефона имеет уникальный характер и используется как основной прикладной идентификатор в большинстве операций. Такой набор полей покрывает одновременно задачи аутентификации, персонализации системной инструкции, контроля платного доступа и вывода сведений в пользовательский профиль.
Вторая базовая сущность описывает чат. В ней хранятся идентификатор владельца, внешний идентификатор диалога, отображаемое название, краткая сводка сна, признак активности и временные метки. Название чата используется в интерфейсе как краткий индекс истории диалогов, а сводка сна применяется для накопления контекста предыдущих обращений пользователя. Признак активности реализует логическое удаление, при котором запись может быть скрыта из обычной выборки без немедленного физического удаления строки из реляционной базы.
Дополнительная сущность предназначена для связки учетной записи пользователя с Telegram-каналом доступа. В ней хранятся идентификатор Telegram, служебные атрибуты профиля, номер телефона, токен и признак подтверждения. Наличие такой сущности показывает, что серверная архитектура ориентирована не только на браузерный интерфейс, но и на возможность подключения внешнего клиента с собственной схемой аутентификации. При этом привязка выполняется через тот же нормализованный номер телефона, что сохраняет единый способ сопоставления учетных записей.
История изменений схемы базы данных организована через последовательность миграций. Сначала формируется базовая таблица пользователей, затем добавляется сущность чатов, после чего схема расширяется дополнительными пользовательскими атрибутами, полями подписки, краткой сводкой сна и счетчиком доступных анализов. Такой способ развития схемы отражает поэтапное уточнение предметной области. Для сопровождения проекта он удобен тем, что каждое структурное изменение зафиксировано как отдельный шаг, а состояние базы данных может быть приведено к актуальной версии автоматически при запуске приложения.
Создание нового чата представляет собой отдельную серверную операцию, а не простое создание пустой записи. После успешной проверки пользователя система формирует персонализированную системную инструкцию, где учитываются имя, дата рождения, количество доступных анализов, стоимость расширенного анализа и набор кратких сводок по предыдущим снам. Затем создается новый идентификатор диалога, сохраняется первоначальное состояние чата, фиксируется указатель на активный диалог и записываются метаданные в реляционную базу. Такой порядок позволяет начинать новый разговор не с пустого контекста, а с уже подготовленной персонализированной среды (см.рис. 26).
```mermaid
sequenceDiagram
    participant C as Клиент
    participant A as Серверный API
    participant D as База данных
    participant P as Шаблон инструкции
    participant S as Сервис диалога
    participant H as Хранилище контекста
    C->>A: Запрос создания чата
    A->>D: Получение пользователя и прошлых сводок
    A->>P: Загрузка базовой инструкции
    A->>S: Формирование персонализированного контекста
    S->>H: Создание состояния нового диалога
    S->>D: Сохранение метаданных чата
    S->>H: Установка активного диалога
    A-->>C: chat_id, title, status
```
Рис. 26. Последовательность инициализации нового чата
Персонализация системной инструкции основана на шаблонном принципе. В подготовленный шаблон подставляются пользовательские данные и сводные результаты прошлых диалогов. При этом в контекст включается только ограниченное число последних кратких описаний снов, что позволяет удерживать персональную историю в компактном виде и не перегружать системную инструкцию длинными архивными данными. Такая стратегия полезна для диалоговой системы, где каждый новый разговор должен учитывать предыдущие темы, но не обязан переносить полную историю старых чатов в системный контекст.
После создания чата система поддерживает механизм переключения активного диалога. Для этого сервер проверяет принадлежность запрошенного чата текущему пользователю, считывает сохраненное состояние и обновляет отдельный указатель на текущую беседу. Благодаря этому последующая отправка сообщений может выполняться без явной передачи идентификатора чата в каждом запросе. Серверная логика получает компактную модель работы: у пользователя есть активный диалог, а все операции отправки, очистки и чтения истории выполняются относительно него.
Наиболее нагруженным участком серверной логики является обработка нового сообщения пользователя. После получения текста система извлекает активный чат, дописывает в его историю новое сообщение и формирует запрос к внешнему AI-сервису. Ответ внешней модели принимается в потоковом режиме и разбирается по частям. Каждый текстовый фрагмент немедленно передается клиенту как отдельное событие, что обеспечивает непрерывное обновление интерфейса. После завершения генерации итоговый ответ добавляется в сохраненную историю диалога и фиксируется в файловом хранилище (см.рис. 27).
```mermaid
sequenceDiagram
    participant C as Клиент
    participant A as Серверный API
    participant S as Сервис диалога
    participant H as Хранилище контекста
    participant AI as Внешний AI-сервис
    participant D as База данных
    C->>A: POST /chat/send-stream
    A->>S: send_message(user, text)
    S->>H: Загрузка активного чата
    S->>AI: Запрос с полной историей сообщений
    loop поток ответа
        AI-->>S: Фрагмент текста
        S-->>A: chunk
        A-->>C: SSE-событие
    end
    S->>D: Обновление названия и сводки сна
    S->>H: Сохранение обновленной истории
    A-->>C: Завершение потока
```
Рис. 27. Потоковая обработка сообщения и возврат ответа клиенту
Особенность прикладной логики заключается в разборе служебных маркеров, которые внешний интеллектуальный модуль может помещать в текст ответа. Сервер ищет в полном сгенерированном ответе маркер переименования диалога и маркер краткой сводки сна. Если такие конструкции присутствуют, сервер обновляет соответствующие поля метаданных чата. В результате один и тот же ответ используется одновременно в двух измерениях: как содержательный текст для пользователя и как источник управляющих данных для дальнейшей организации истории диалогов.
Наряду с потоковым режимом система поддерживает и асинхронный режим обработки сообщений через очередь задач. В этом варианте запрос пользователя не удерживает HTTP-соединение до конца генерации. Вместо этого сообщение ставится в очередь, пользователю возвращается идентификатор фоновой задачи, а получение результата выполняется отдельным запросом статуса. Для обработки используется связка брокера сообщений и воркера задач, который запускает ту же прикладную логику общения с интеллектуальным модулем. Такой режим полезен для сценариев, где немедленный потоковый вывод не обязателен, а серверу требуется развести сетевой запрос и длительную обработку по разным контурам (см.рис. 28).
```mermaid
sequenceDiagram
    participant C as Клиент
    participant A as Серверный API
    participant R as Redis/Celery
    participant W as Воркер
    participant S as Сервис диалога
    participant AI as Внешний AI-сервис
    C->>A: POST /chat/send
    A->>R: Постановка задачи в очередь
    A-->>C: task_id
    R->>W: Доставка задачи
    W->>S: Обработка сообщения
    S->>AI: Генерация ответа
    AI-->>S: Полный ответ
    S-->>W: Результат обработки
    W->>R: Сохранение статуса и результата
    C->>A: GET /chat/task/{id}
    A->>R: Чтение статуса
    R-->>A: processing или result
    A-->>C: Текущее состояние задачи
```
Рис. 28. Асинхронная обработка сообщения через очередь
Серверный слой поддерживает полный цикл операций над историей чатов. Пользователь может получить список собственных диалогов, переключиться на один из них, прочитать сохраненную историю, изменить отображаемое название и выполнить удаление. Список диалогов возвращается в порядке последнего изменения, что упрощает клиентское отображение актуальных бесед. При очистке активного чата система сохраняет только системные сообщения, удаляя пользовательскую и ассистентскую часть переписки. При удалении используется мягкая деактивация записи в базе данных и физическое удаление соответствующего JSON-документа из файлового хранилища (см.рис. 30).
```mermaid
flowchart TD
    CREATE[Создание чата] --> META[Запись метаданных]
    META --> ACTIVE[Назначение активного диалога]
    ACTIVE --> DIALOGUE[Обмен сообщениями]
    DIALOGUE --> RENAME[Переименование]
    DIALOGUE --> CLEAR[Очистка до системного контекста]
    DIALOGUE --> SWITCH[Переключение на другой чат]
    DIALOGUE --> DELETE[Удаление чата]
    RENAME --> DIALOGUE
    CLEAR --> DIALOGUE
    SWITCH --> DIALOGUE
    DELETE --> DEACTIVATE[Деактивация метаданных и удаление контекста]
```
Рис. 30. Операции создания, очистки, переименования и удаления чата
Гибридное хранение истории диалогов реализовано по пользовательским каталогам. Для каждого пользователя формируется отдельная область хранения, внутри которой располагаются JSON-документы отдельных чатов и служебный указатель на текущую активную беседу. Полный контекст каждого диалога сохраняется как массив сообщений с ролями и временными метками. Подобная схема позволяет быстро загружать содержимое конкретного разговора, не извлекая длинные текстовые массивы из реляционной базы данных. Для прикладного сценария с текстовой перепиской такая архитектура является компромиссом между структурированной метаинформацией и объемным контекстом сообщений (см.рис. 29).
```mermaid
flowchart TD
    API[Серверная логика] --> DB[(Реляционное хранилище)]
    API --> JSON[(Контекст диалогов)]
    DB --> U1[Пользовательский профиль]
    DB --> U2[Метаданные чатов]
    DB --> U3[Подписка и счетчики]
    JSON --> J1[Полная история сообщений]
    JSON --> J2[Указатель на активный диалог]
```

Взаимодействие с внешним AI-сервисом построено как stateless-обмен. Это означает, что внешний провайдер не хранит состояние диалога на своей стороне, а получает полный контекст сообщений в каждом новом запросе. Для этого сервер сериализует системные, пользовательские и ассистентские сообщения в стандартный набор ролей и передает его в запросе генерации. Такой подход увеличивает объем каждого обращения, но сохраняет контроль над историей диалога внутри собственной серверной инфраструктуры и не связывает приложение с закрытым состоянием внешнего поставщика модели.
Отдельным аспектом серверной логики является устойчивость к частичным сбоям. При старте приложения выполняются повторные попытки подключения к базе данных, при сбоях миграций используется дополнительная защитная инициализация схемы, а при ошибках потоковой генерации клиент получает отдельное сообщение об ошибке внутри того же механизма событий. Для эксплуатационной модели это означает, что система не ограничивается только прямым выполнением основной логики, но и содержит вспомогательные процедуры, направленные на снижение числа аварийных остановок при запуске и обработке запросов.
Серверный API дополнен служебным маршрутом проверки состояния приложения. Он возвращает признак доступности сервиса и текущее время на стороне сервера, что позволяет использовать его в механизмах контейнерного healthcheck и внешнего мониторинга. Наличие такого маршрута оправдано в многокомпонентной системе, где веб-интерфейс, база данных, очередь задач и внешний AI-провайдер образуют общую цепочку обслуживания. Для эксплуатационного контура требуется явный признак того, что прикладной сервер поднят и способен принимать запросы.
Таким образом, серверная часть приложения реализует не только набор HTTP-маршрутов, но и полноценную прикладную среду, в которой объединены аутентификация по номеру телефона, управление профилем и подпиской, персонализированное создание чатов, потоковая и фоновая обработка сообщений, автоматическое извлечение метаданных из ответа модели, мягкое удаление диалогов и гибридное хранение истории. Принятая архитектура сочетает реляционную модель для устойчивых сущностей, файловое хранение для длинного текстового контекста, очередь задач для длительных операций и stateless-интеграцию с внешним интеллектуальным сервисом, что соответствует функциональным требованиям рассматриваемого веб-приложения.
